## Matching Rules

- Treat a test as the same behavior only when the setup, operation, expected result, and failure mode agree.
- A SQL-baseline test is not redundant with a result-only test: keep both when SQL shape is part of the provider contract.
- A provider override that changes only SQL should map to the shared behavior; an override that changes results or throws needs its own capability record.
- Prefer EF Core’s canonical test name when importing a test unchanged. Use a descriptive local name only for tests belonging to the shared ADO.NET contract.

## Next Import Batch

Start with the high-confidence, result-oriented families: generated keys, default-value inserts, mapped-type round trips, paging results, transactions, and portable migrations. Defer JSON, inheritance, spatial, provider-specific functions, and SQL-baseline-heavy suites until their capability and fixture requirements are modeled.

## Inventory Count

The provider-suite records give a more useful bound than the behavior rows above. The inherited totals are execution counts summed across concrete provider classes, not unique test methods. Comparing unique specification-base names and taking the largest method count reported for each base produces this distribution:

| Presence in upstream provider inventories | Additional methods | Interpretation |
|---|---:|---|
| All 5 providers | 200 | Strong candidates for the shared core suite; these include `ConferencePlannerTestBase` (22), `MigrationsSqlGeneratorTestBase` (49), `ModelBuilding101RelationalTestBase` (124), `SeedingTestBase` (2), and `TwoDatabasesTestBase` (3) |
| 4 of 5 providers | 2,181 | Strong candidates after capability and flatfile review |
| 3 of 5 providers | 236 | Possible shared tests, but more provider-specific behavior is likely |
| 2 of 5 providers | 563 | Usually conditional or provider-specific |
| 1 of 5 providers | 1,354 | Provider-only candidates, not common tests by default |
| **Base families absent from the documented intersection** | **4,655** | Additional base families, not a direct method count |

Taking the maximum method count for every unique base yields an upper-bound union of **15,233 inherited test methods** across the five provider inventories. Subtracting the existing 6,093 intersection gives up to **9,140 additional method slots**. This is an upper bound because the records provide counts per base, not method-level identity, and some differences are version or provider-variant counts rather than genuinely new behaviors.

For context, the recorded inherited execution totals are approximately SQL Server 19,413, SQLite 14,670, PostgreSQL 13,166, MySQL 11,770, and DuckDB 12,500 (lower bound): about **71,519 inherited executions** before adding this project’s sixth provider. Those repetitions are valuable runtime coverage, but they should not be counted as 71,519 unique common tests.

The definitive six-provider count requires a method-level union followed by the flatfile capability matrix. The likely range is therefore **6,093 to 15,233 unique shared candidates**, with the upper end including tests that may require skips, capability declarations, or provider-specific setup.
